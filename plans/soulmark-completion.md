## 基线与原则

基线见 `artifacts/soulmark-audit-2026-10-20.md`：按现有构建调用，1811 条实际魂印记录中，930 条有输出且无残留，801 条部分解析，77 条无输出，3 条正文被静默跳过。解析无残留不等于行为验收完成。

- 保留已有工作区改动，不修改 hash 算法、常量或版本。
- 按完整精灵 ID 区分形态，不按重复的 petNo 合并。
- 未能表达的条件和效果必须留下原句及原因，不得移除条件后执行效果。
- 优先复用已有 hook、条件、表达式和原子 op；新的精灵差异用内容数据表达。
- 按 `plans/add-effect.md` 小步实施，不整库重建内容、不覆盖官方覆盖率文件、不重生成 parser golden。

## 第一阶段：正确性和可追踪性

1. 修复未知条件下效果无条件生成及其继承、成功/失败分支串接；保留独立的有效效果。
2. 修复 FAQ 正文提取，确保带实际规则的文本不被当作无内容跳过；未支持部分仍明确留档。
3. 统一生产构建和编译检查的解析参数，避免传名称与不传名称产生两套统计。
4. 添加默认只读的实时审计入口，分别统计无特性、空输出异常、未解析、部分解析和无残留；逐条比较内容包并区分收录范围和默认装配策略。

审查要点：未知条件后的省略主语、同触发器尾句、else 不得逃逸；遇到独立明确触发器后应能恢复正常解析。FAQ 处理不得把攻略噪声造为规则。

先根据实时残留审计选取收益明确、已有引擎可表达的句式家族，逐条补规则和正反例。检查已有测试是否锁住错误时序，例如技能使用效果被当作战斗开始效果；错误行为应修正，不以通过旧快照代替验证。

确实缺少事件上下文、资源和形态状态机、场下选择器、历史记录等能力时，先独立设计通用契约，再实现插件和内容数据。不得为单只精灵增加核心引擎分支。

## 独立契约：施加时固定幅值

审查确认：现有持久化 `amountExpr` 会随每次结算重新读取数值，不能等价表达“回合开始时读取 n，并将本次 n 用于当回合”。因此单独增加 `apply_status.amountTiming: "apply"`；缺省仍为原有动态行为。

- 适用已有三个数值 modifier 轴：`dmgOutPct`、`dmgReduceFlat`、`dmgFlat`，且必须具有 `amountExpr` 或兼容格式转换得到的表达式。
- 在效果落地时，以最终持有者为 `self`、其对手为 `foe`、持有者为默认 `target` 求值，将结果存为已有 `amountExpr` 的数字字面量。
- 该选项属于输入 IR，不增加战斗状态字段；重施加重新固定数值。版本和 hash 逻辑不变。
- 实现触点：内容 schema、`CompiledEffect`、共享语义校验、施加处理函数、针对行为测试。它与具体魂印规则及内容同步分开实施和审查。
- 验收：三轴与缺省动态行为对照，施加给对手的视角、兼容旧幅值、零值、重施加、JSON 恢复及真实伤害结果；无幅值、错误轴或错误 op 必须拒绝。

### 吸取原子结算的收尾

实际包反例证明：`hp_delta.healSelf` 若在 checkpoint 之后执行，吸完对手最后体力会直接终局而漏掉回血。依照普通伤害的吸取顺序，本次扣血依赖的 `healSelf` 和 `benchHeal` 应在 checkpoint 前完成，然后统一派发 KO/替补/终局；仍保留持有者存活检查，禁止自伤致死后靠吸取复活。验收包括实际扣量封顶、非致死、终局事件顺序、替补续跑不重复和自伤致死。
